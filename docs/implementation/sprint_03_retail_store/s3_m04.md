# S3-M04 - Liveness/readiness probes and resource requests/limits

**Sprint:** S3 Retail Store & DynamoDB (PDF Step 3 (2.5 h))  
**Owner:** B  
**Estimate:** 1 h  
**Depends on:** S3-M02  
**Teacher's requirement:** Deliverable 3 'liveness/readiness probes'; Step 7 HPA needs CPU requests

## Why this issue exists
The rubric lists probes. Probes are also what make rolling updates safe (S7: a bad image never becomes Ready). CPU requests are mandatory for the HPA to compute utilisation.

## Steps
1. Audit the rendered manifest: for each of the 5 deployments note existing livenessProbe/readinessProbe. The upstream manifest already has some; add the missing ones in a kustomize patch, do not duplicate.
2. Add resources.requests and resources.limits (cpu, memory) to each deployment based on `kubectl top pods -n retail` observations. Put `ui` requests.cpu at a realistic value (for example 200m) so HPA percentages make sense.
3. Set the rollout strategy of `ui` explicitly (RollingUpdate, maxUnavailable 0, maxSurge 1) for the S7 rollback demo.
4. Table in k8s/README.md: service / probe path / requests / limits.

## Useful commands
```bash
kubectl get deploy -n retail -o custom-columns=N:.metadata.name,L:.spec.template.spec.containers[0].livenessProbe.httpGet.path,R:.spec.template.spec.containers[0].readinessProbe.httpGet.path
kubectl top pods -n retail
```
