# S6-M01 - Terraform: SNS topic + CloudWatch alarm on node CPU > 75%

**Sprint:** S6 CloudWatch & Serverless Remediation (PDF Step 6 (3 h))  
**Owner:** C  
**Estimate:** 1 h  
**Depends on:** S2-M04  
**Teacher's requirement:** PDF Step 6 'CloudWatch alarm on EKS node CPU (> 75%) linked to an SNS topic'

## Why this issue exists
This is the cloud-side (AWS-native) monitoring path that complements Prometheus.

## Steps
1. terraform/modules/alerting: aws_sns_topic shopops-alerts.
2. aws_cloudwatch_metric_alarm: namespace AWS/EC2, metric CPUUtilization, dimension AutoScalingGroupName = ASG name output from S2-M04, statistic Average, period 300, evaluation_periods 1 (or 2), threshold 75, comparison GreaterThanThreshold, alarm_actions = [SNS topic], treat_missing_data notBreaching.
3. Test the plumbing: `aws cloudwatch set-alarm-state --alarm-name <name> --state-value ALARM --state-reason test`. Subscribe your email to the topic first to see the message arrive (optional).

## Useful commands
```bash
aws cloudwatch describe-alarms --alarm-names shopops-node-cpu-high
```

## Done when (acceptance checklist)
- [ ] Alarm and topic created by Terraform, destroyed by `make down`.
- [ ] set-alarm-state publishes to SNS (email received or Lambda invoked later).
- [ ] PR reviewed by a different member and merged; commit messages start with the local ID
- [ ] Nothing secret committed (keys, tokens, kubeconfig, tfstate)

## Watch out
- Basic EC2 monitoring has 5-minute granularity, so the alarm reacts after minutes, not seconds.

## Out of scope (do not do here)
- Lambda.

Topic ARN available for the Lambda subscription.
