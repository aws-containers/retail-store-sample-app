## Why this issue exists
The PDF provides a first Jenkinsfile. We keep its structure and fix three things: Trivy used --exit-code 0 so it could never fail the build; the ECR login pointed at the repository instead of the registry host; and image tags should be traceable.

## Steps
1. Create /Jenkinsfile at the repo root (declarative pipeline). Stages: Init (compute account id, registry, image name) -> Build -> Trivy scan -> Push -> (Deploy is added in S4-M05).
2. Build: `docker build -t $IMAGE src/ui` (verify the Dockerfile really is in src/ui in the pinned upstream code). Tag = ${BUILD_NUMBER} plus the short git SHA.
3. Trivy: `trivy image --severity CRITICAL --ignore-unfixed --exit-code 1 --no-progress $IMAGE`. `--ignore-unfixed` avoids permanently red builds caused by CVEs that have no fix yet.
4. Push: `aws ecr get-login-password | docker login --username AWS --password-stdin <account>.dkr.ecr.us-east-1.amazonaws.com` then docker push.
5. post { always { docker image prune -f; cleanWs() } } so the small disk does not fill.
6. Prove Trivy blocks: temporarily build FROM an old vulnerable base image on a branch, confirm the stage fails, then revert. Save a screenshot.

## Useful commands
```bash
trivy image --severity CRITICAL --ignore-unfixed --exit-code 1 --no-progress <image>
aws ecr list-images --repository-name retail-ui
```

## Done when (acceptance checklist)
- [ ] Build runs from Jenkins on demand and the image appears in ECR.
- [ ] Trivy stage fails on a deliberately vulnerable image (screenshot in docs/evidence/).
- [ ] No AWS key anywhere; uses the instance role.
- [ ] Disk cleanup in post.
- [ ] PR reviewed by a different member and merged; commit messages start with the local ID
- [ ] Nothing secret committed (keys, tokens, kubeconfig, tfstate)

## Watch out
- First Trivy run downloads its vulnerability database (slow). Subsequent runs are faster.
- The first build of the Java image is slow on a small instance; run it once manually before demos.
