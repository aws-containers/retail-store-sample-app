# S4-M05 - Deploy stage: Jenkins updates the cluster and checks the rollout

**Sprint:** S4 Jenkins CI/CD Pipeline (PDF Step 4 (3.5 h))  
**Owner:** B  
**Estimate:** 1.5 h  
**Depends on:** S4-M03, S3-M02  
**Teacher's requirement:** PDF Step 4 'kubectl set image -> rollout status'; Deliverable 2 'EKS deployment, and rollout verification'

## Why this issue exists
The last stage of the pipeline. The difficulty: Jenkins runs as LabRole, but inside Kubernetes, being an IAM role is not enough - the role also needs permission in the cluster. The cluster creator (your lab session) is admin automatically; the Jenkins instance is not. So kubectl may answer 'Unauthorized' even though the AWS CLI works.

## Steps
1. Add stage 'Deploy': `aws eks update-kubeconfig --name eks-shopops --region us-east-1`, `kubectl set image deployment/ui ui=$IMAGE -n retail`, `kubectl rollout status deployment/ui -n retail --timeout=180s`. Check the container name first: `kubectl get deploy ui -n retail -o jsonpath='{.spec.template.spec.containers[*].name}'`.
2. SPIKE (30 min max, do it first): on the Jenkins box run `kubectl get pods -n retail`. If it works, continue. If 'Unauthorized': LabRole is also the node role, so EKS already has an access entry for it of the node type, and node-type entries cannot receive admin policies (to verify with `aws eks list-access-entries` / `describe-access-entry`).
3. Fallback that does not depend on IAM: create a ServiceAccount `jenkins-deployer` in namespace retail + Role allowing get/list/patch on deployments and pods + RoleBinding, create a token for it, build a kubeconfig that uses the token, and store it in Jenkins as a 'secret file' credential. Automate token creation in `make up`. Least privilege, no cluster-admin.
4. Record which option worked in docs/jenkins_cluster_access.md (professor-facing explanation).
5. Image pull: nodes pull from ECR with the node role. If pods show ImagePullBackOff with 'no basic auth credentials', check ECR read permissions of LabRole.

## Useful commands
```bash
# on Jenkins instance
aws eks update-kubeconfig --name eks-shopops --region us-east-1
kubectl auth can-i patch deployments -n retail
kubectl rollout status deployment/ui -n retail
```

## Done when (acceptance checklist)
- [ ] Pipeline ends green: new tag running (`kubectl get deploy ui -n retail -o jsonpath='{.spec.template.spec.containers[0].image}'`).
- [ ] Rollout verified by the pipeline itself (`rollout status`).
- [ ] Access method documented with its trade-offs.
- [ ] PR reviewed by a different member and merged; commit messages start with the local ID
- [ ] Nothing secret committed (keys, tokens, kubeconfig, tfstate)

## Watch out
- This is the riskiest issue of the sprint: start the spike early in the sprint, not on the last day.
- A failed rollout makes `rollout status` exit non-zero, which fails the build - that is the intended behaviour.
