# S1-M03 - Terraform remote state: S3 bucket + DynamoDB lock table

**Sprint:** S1 Initialization & FinOps (PDF Step 1 (1 h))  
**Owner:** A  
**Estimate:** 45 min  
**Depends on:** S1-M01  
**Teacher's requirement:** PDF section 3, Step 1, action 3 (second half); Deliverable 1 (S3/DynamoDB remote state)

## Why this issue exists
Terraform needs somewhere to store its state. The PDF requires a remote state in S3 with a DynamoDB lock table. This is created BEFORE the main Terraform (chicken and egg), by a small idempotent script, because the state bucket must survive `terraform destroy`.

## Steps
1. Create scripts/bootstrap_state.sh (idempotent: running it twice must not fail). It must work in ANY account, so the bucket name is shopops-tfstate-<account_id> (S3 names are globally unique).
2. Bucket settings: versioning on, default encryption (AES256), block all public access. In us-east-1 do not pass a LocationConstraint.
3. Lock table: name shopops-tflock, partition key LockID (String), PAY_PER_REQUEST.
4. Create terraform/envs/lab/backend.tf with an EMPTY backend 's3' block and pass bucket/key/region/table at init time (partial configuration) so no account id is hardcoded in Git.
5. Add `make bootstrap` that runs the script and `make init` that runs terraform init with the -backend-config flags.

## Useful commands
```bash
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
BUCKET=shopops-tfstate-$ACCOUNT
aws s3api create-bucket --bucket $BUCKET --region us-east-1
aws s3api put-bucket-versioning --bucket $BUCKET --versioning-configuration Status=Enabled
aws dynamodb create-table --table-name shopops-tflock --attribute-definitions AttributeName=LockID,AttributeType=S --key-schema AttributeName=LockID,KeyType=HASH --billing-mode PAY_PER_REQUEST
terraform init -backend-config="bucket=$BUCKET" -backend-config="key=lab/terraform.tfstate" -backend-config="region=us-east-1" -backend-config="dynamodb_table=shopops-tflock"
```

## Watch out
- Recent Terraform versions mark `dynamodb_table` as deprecated in favour of `use_lockfile` (S3 native locking). It still works; we keep the DynamoDB table because the PDF's rubric asks for S3/DynamoDB state. Read the init warning, do not panic.
- The bucket and table are NOT destroyed by `make down` (otherwise the state would be lost mid-destroy).

## Out of scope (do not do here)
- VPC/EKS resources (S2).
